# Trilogue 現状報告書（教授向け）— Phase 2-A: LabVIEW連携 第一段階

## 1. 報告概要

先生からご指摘いただいた **「LabVIEWへのパッケージ化」** および **「技術プロセスの透明化」** を受け、
LabVIEW（LV）をクライアントとする構成へ移行する第一段階に着手し、**完了した**。

合意していた第一段階のゴール「**LVから送信し、LVにAIの返信が返る**」を実機で達成した。
DLL化は当面追わず、開発効率と汎用性を優先して **HTTP直結方式** で実装している。

---

## 2. 第一段階の目標と到達状況

### 2.1 目標（先生と合意した範囲）
- LV をフロントエンドのクライアントに据える
- LV ⇄ 自作サーバー間を HTTP/JSON で直結する
- 「LVから投げて、LVに返ってくる」往復の成立（＝第一段階クリア条件）
- DLL には拘らず、楽で汎用化できる方向で進める

### 2.2 到達状況（結論）
**達成済み**
- LV専用のHTTPエンドポイントをサーバーに新設
- LV から送信 → AI応答受信 → LV画面表示までの往復を実機確認
- 別PC間（Windows=LV ↔ Mac=サーバー）での同一LAN通信を確認
- マルチエージェント化の足場（`agentId` による複数AI切替）を先行実装
- 通信経路・技術仕様の透明化（本書 第5章）

**次フェーズ**
- 複数AIをLV上で同時に提示するUI
- 会話履歴の保持・永続化

## 3. システム構成（現行）

```txt
[LabVIEW (Windows)]
   │  HTTP POST (JSON, UTF-8)
   ▼
[自作APIサーバー (Next.js / Node.js, Mac)]
   │  HTTPS (REST)
   ▼
[OpenAI API (gpt-4o-mini)]
   │
   ▼ 返信JSON
[サーバー] → [LabVIEW で表示]
```

- LV → 自作サーバー: **HTTP**（同一LAN、`http://<サーバーIP>:3000`）
- 自作サーバー → LLM: **HTTPS**（`https://api.openai.com/v1/chat/completions`）
- APIキーは**サーバー側の環境変数のみ**で保持し、LVへは一切渡さない

---

## 4. 今回の実装内容（詳細）

### 4.1 LabVIEW専用APIの新設
Web UI用の既存API（入れ子の `messages[]` を要求）とは別に、
**LVが組み立て・解析しやすい平坦JSON**の専用エンドポイントを用意した。

- `POST /api/lv/chat` — 対話本体
  - 入力: `{ "text": "...", "agentId": "alpha" }`（最小は `text` のみ）
  - 出力: `{ "ok", "reply", "agentId", "agentName", "model", "error" }`
  - HTTPステータスは常に200とし、成否は `ok` で判定 → LV側のステータス分岐を不要化
- `GET /api/lv/agents` — エージェント一覧取得／疎通確認（ヘルスチェック兼用）

### 4.2 マルチエージェントの足場
`agentId`（`alpha` / `beta` / `gamma`）で、人格・モデルを切り替え可能にした。
LV側は `agentId` を変えるだけで「AIごとの差」を出せる構造。

### 4.3 内部設計の整理
LLM呼び出しとエージェント定義を共通部品として分離し、Web用とLV用が同一処理を共有する構成にした。
これにより、LLMプロバイダの差し替え（OpenAI↔Gemini等）も一箇所の修正で対応可能な土台となっている。

### 4.4 LabVIEW側VI
LV標準の **HTTP Client VIs** と **Flatten/Unflatten To JSON** のみで構成。
`Trilogue Chat.vi` 相当の VI を作成し、文字列入力 → 送信 → AI返信表示の往復を確認した。
（DLLや外部ライブラリは不使用）

## 5. 通信プロセスの透明化（先生ご指摘事項）

| 項目 | 内容 |
| --- | --- |
| プラットフォーム | OpenAI（gpt-4o-mini）を主軸 |
| サーバー言語 | Node.js / TypeScript（Next.js Route Handlers） |
| 通信プロトコル | LV→サーバー: HTTP / サーバー→LLM: HTTPS (REST) |
| データ形式 | JSON (UTF-8) |
| 認証 | APIキーはサーバー環境変数のみ。クライアント露出なし |

**リクエストの流れ**
1. LV が `POST /api/lv/chat` に平坦JSONを送信
2. サーバーがAPIキーとエージェント定義（人格・モデル）を付与
3. サーバーが OpenAI へHTTPSでリクエスト
4. 返信を平坦JSONに整形してLVへ返却

**開発上の留意点（実態）**
- LabVIEW 2016 上でも、UTF-8の日本語応答が**文字化けせず正しく表示**されることを実機で確認した。
- ネットワークは別PC間（Windows/Mac）でも、同一LAN・ポート開放の条件下で安定動作を確認。

---

## 6. 動作確認結果

- `GET /api/lv/agents`: 正常（エージェント一覧返却を確認）
- `POST /api/lv/chat`（異常系 text空）: `ok:false` とエラー文返却を確認
- `POST /api/lv/chat`（正常系）: `ok:true` とAI返信返却を確認
- LV実機: `User Text` 入力 → Run → `Reply` にAI返信表示を確認
- 別PC往復（Windows LV ↔ Mac サーバー）: ブラウザ疎通＋LV往復ともに成功

### サーバーログ実測値（テスト時）
```text
GET  /api/lv/agents 200 in 176ms   ← LV機ブラウザでの疎通確認
GET  /api/lv/agents 200 in  40ms   ←（同上 2回目）
POST /api/lv/chat   200 in  2.3s   ← LVからの送信→AI返信の往復
```
- `POST /api/lv/chat` が **200（正常）** を返しており、LV往復の成立を確認。
- 所要2.3秒の内訳は、サーバー処理が約136ms、残り約2.2sはOpenAIの応答待ち。
  → 遅延の主因はLLM側であり、自作サーバーのオーバーヘッドは小さいことを確認。
